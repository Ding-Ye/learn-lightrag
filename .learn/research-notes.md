## Has LLM call layer? (decides Phase G)

**YES.** LightRAG is fundamentally LLM-driven; it makes calls in three places:

1. **Entity/relationship extraction** during ingestion — `lightrag/operate.py` `extract_entities()` (cited by A2 around L2883-3163; verified that operate.py contains `_process_extraction_result`, `_rebuild_from_extraction_result`, `_rebuild_single_entity` — the extraction pipeline).
2. **Description summarization** — when same entity is seen in many chunks, LLM merges descriptions via `_handle_entity_relation_summary()` in `operate.py:167-303`.
3. **Final answer synthesis** — every query mode passes a context-augmented prompt to `llm_model_func` for the final response.

**Provider abstraction:** LightRAG uses dependency injection — the user passes `llm_model_func: Callable` into the constructor. Wrappers exist in `lightrag/llm/` for OpenAI, Azure, Anthropic, Ollama, Bedrock, Hugging Face, Google Gemini.

**Implication for our learn-lightrag:** Phase G is **REQUIRED**. We will provide a Go `Provider` interface and implement OpenAI as the default backend; the multi-model addendum will document one-line provider swaps.

## Section A1 — Top-level architecture (lightly normalized)

### Pitch

LightRAG is a "Simple and Fast Retrieval-Augmented Generation" framework from HKUDS that combines **dual-level retrieval** — vector similarity search on document chunks **plus** knowledge-graph entity/relation traversal — to outperform vanilla RAG and competitive systems like GraphRAG through LLM-extracted structured knowledge representation. Released alongside the EMNLP 2025 paper.

### Black-box use case (from README quickstart)

```bash
export OPENAI_API_KEY="sk-..."
curl https://raw.githubusercontent.com/gusye1234/nano-graphrag/main/tests/mock_data.txt > ./book.txt
python examples/lightrag_openai_demo.py
```

The script: configures an OpenAI LLM backend, loads a text document, initializes storages asynchronously, inserts the document (triggering chunking → embedding → entity extraction → graph construction), then queries across four modes (`naive`, `local`, `global`, `hybrid`), each returning ranked results with source attribution.

### 9. Query Modes (Naive / Local / Global / Hybrid / Mix / Bypass)
**File:** `lightrag/operate.py:3164-3410` `kg_query` orchestrator + `:3516-4055` retrieval helpers + `:4930-5200` `naive_query`
**Distinguishing feature:** Six retrieval strategies:
- **Naive** — vector similarity on chunks only; no graph (baseline).
- **Local** — entity-centric; top-k entities by keyword match, gathers connected chunks/relations.
- **Global** — relation-centric; top-k relationships, expands to related entities, synthesizes overview.
- **Hybrid** — combines local + global in single LLM call.
- **Mix** — heuristic selector chooses mode based on query / runs both with reranker.
- **Bypass** — skips retrieval entirely; raw query → LLM (diagnostic).

Each mode compiles a context window, applies token truncation (entity/relation/chunk budgets), optionally reranks chunks before LLM synthesis.

**Core data shape:**
```python
async def kg_query(
    query: str,
    graph_storage: BaseGraphStorage,
    entities_vdb: BaseVectorStorage,
    relationships_vdb: BaseVectorStorage,
    text_chunks: BaseKVStorage,
    param: QueryParam,
    global_config: dict,
) -> dict:
```

**MVS for Go port (one chapter, multiple funcs):** `QueryNaive(q string, k int) (string, error)`, `QueryLocal(q string, k int) (string, error)`, `QueryGlobal(q string, k int) (string, error)`, `QueryHybrid(q string) (string, error)`. Mix/Bypass deferred to docs as exercises.

### 10. Incremental Rebuild from Cache
**File:** `lightrag/operate.py:560-846` `rebuild_knowledge_from_chunks` + `:847-936` cache retrieval + `:1101-1623` rebuild helpers
**Distinguishing feature:** Reconstructs entity/relationship data from cached LLM extractions during pipeline recovery / large-scale ingestion. Semaphore-controlled parallel processing. Keyed locks per entity/relationship to prevent races. Sorts cached results by creation_time for deterministic ordering. `source_ids_limit` truncation strategy (KEEP oldest vs FIFO newest). Reports progress via `pipeline_status` async object. Early termination on first exception via `PipelineCancelledException`.

## Glossary (deduplicated, 18 terms)

| Term | Plain English |
|---|---|
| **doc-status** | Each ingested document has a state machine (PENDING → PROCESSING → PROCESSED/FAILED) tracked in a separate KV store. Enables resume-on-failure and progress monitoring. |
| **namespace** | String prefix (e.g. `"rag_v1:"`) isolating multiple LightRAG instances sharing one storage backend. Prevents cross-talk. |
| **gleaning** | N-round extraction loop. After initial extraction, N continuation prompts ask "Any more entities?" to iteratively improve recall. |
| **chunk_token_size / chunk_overlap_token_size** | Defaults 1200 / 100. Overlap preserves context across chunk boundaries. |
| **source_ids** | Ordered list of chunk IDs that mention an entity/relationship. Used for citation, dedup, and truncation decisions. |
| **source_ids_limit** | Truncation strategy (KEEP oldest vs FIFO newest) when source list grows too large. |
| **high-level vs low-level keywords** | Global mode uses high-level (themes, concepts); local mode uses low-level (specific entity names). LLM extracts both from the query. |
| **kg_query** | Main orchestrator for graph-backed queries; dispatches to local/global/hybrid based on `QueryParam.mode`. |
| **map-reduce summarization** | Consolidates many descriptions of one entity into a single summary, via LLM if heuristic threshold exceeded. |
| **reranking** | Optional post-retrieval step using a cross-encoder to re-score retrieved chunks for the final query. |
| **embedding_func** | Callable wrapper with `embedding_dim` and `max_token_size` metadata fields. User passes any provider. |
| **llm_response_cache** | KV store keyed by `mode:cache_type:hash` to avoid redundant LLM calls on the same input. |
| **bypass mode** | Query mode that skips KG entirely; raw query → LLM. Diagnostic. |
| **pipeline_status** | Shared async object tracking ingestion progress across docs. Supports user cancellation via `PipelineCancelledException`. |
| **QueryParam** | Single-query config dataclass (mode, top_k, conversation_history, rerank flag, token budgets). |
| **TextChunkSchema** | Pydantic model for one chunk: `tokens`, `content`, `chunk_order_index`, `full_doc_id`. |
| **KnowledgeGraph / KnowledgeGraphNode / KnowledgeGraphEdge** | Pydantic models in `lightrag/types.py` returned by `get_knowledge_graph()` for the Web UI to render. |
| **storage factory string** | `kv_storage="JsonKVStorage"` etc. — a name looked up via factory dict to select the impl class. Our Go port uses interface impls + functional options instead. |

## Anti-patterns from upstream we will NOT repeat

1. **Dict-shaped contracts** (`dict[str, Any]` everywhere) → use Go structs.
2. **Dual sync/async APIs** (`insert` + `ainsert`) → Go uses goroutines + context, single API per operation.
3. **60+ optional ctor params** → split into `Config` struct + functional options pattern.
4. **`**global_config` dict propagation** → explicit struct passing.
5. **Exception-based control flow** (`PipelineCancelledException`) → `context.Context` cancellation.
6. **String factory keys** (`kv_storage="JsonKVStorage"`) → interface satisfaction + DI.
7. **Inline legacy migration logic** → version field + fail-fast on unknown.

## Open questions / risks

1. **operate.py is huge (~5K LOC).** WebFetch summarization may miss details on later chapters. Subagents writing s07-s10 should fetch in slices (e.g. `operate.py` lines 2800-3200) using GitHub line-anchor URLs.
2. **Tokenizer dependency.** Upstream uses `tiktoken` (cl100k_base). Go has third-party tiktoken bindings; pick one in s03 (`pkoukk/tiktoken-go` is the de-facto port).
3. **Embedding provider in s01.** OpenAI embeddings need API key. We'll keep the default OpenAI but allow `-provider mock` flag that produces deterministic fake embeddings for offline CI.
4. **NanoVectorDB equivalent in Go.** No direct port. We implement a minimal in-memory cosine-similarity index (~80 LOC) — plenty for teaching purposes.
5. **NetworkX equivalent.** We implement a minimal undirected graph with adjacency map (~100 LOC). Extension to neo4j-driver-go can be appendix.
6. **Async semantics.** Python's asyncio cooperative concurrency vs Go's preemptive goroutines + channels. Cover this trade-off explicitly in s09 README.
